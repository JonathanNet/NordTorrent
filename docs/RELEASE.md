# Publishing releases

NordTorrent ships three things per release:

| Asset | Who builds it | Where |
| --- | --- | --- |
| `nordtorrent-<version>-windows-x64.zip` | GitHub Actions (windows-latest) | Release assets |
| `nordtorrent-<version>-linux-x64.tar.gz` | GitHub Actions (ubuntu-latest) | Release assets |
| `nordtorrent-<version>-source.zip` | GitHub Actions (or `git archive` locally) | Release assets |

GitHub also attaches its own `Source code (zip)` and `Source code (tar.gz)` to every release, so the repository itself is always downloadable from the **Code** button and from the release page.

## Cut a release

```bash
# 1. make sure main is pushed
git push origin main

# 2. tag the version in server/Cargo.toml
git tag v0.1.0
git push origin v0.1.0
```

Pushing the tag starts `.github/workflows/release.yml`, which:

1. builds the server on Windows and Linux with `cargo build --release --locked`
2. packages the binary with the launcher and docs
3. uploads both zips as workflow artifacts
4. creates a GitHub Release for the tag and attaches the assets, with generated release notes

The workflow uses `softprops/action-gh-release@v2`, so no token setup is needed beyond the default `GITHUB_TOKEN` (declared in the workflow as `permissions: contents: write`).

## Build the Windows zip locally

The maintainer keeps a small local helper for this (`scripts/package-windows.ps1`). It is not part of the published tree, because that folder also holds deployment credentials. The equivalent manual steps:

```powershell
# NASM must be on PATH for aws-lc
cargo build --release --locked --manifest-path server/Cargo.toml

$version = (Select-String server/Cargo.toml -Pattern '^version\s*=\s*"([^"]+)"').Matches[0].Groups[1].Value
$stage = "stage/nordtorrent-$version-windows-x64"
New-Item -ItemType Directory $stage -Force | Out-Null
Copy-Item server/target/release/nordtorrent.exe $stage
Copy-Item packaging/windows/run-nordtorrent.cmd, packaging/windows/README.txt $stage
Copy-Item README.md, README.da.md, LICENSE $stage
Compress-Archive "$stage/*" "dist/nordtorrent-$version-windows-x64.zip"
```

The zip contains:

```
nordtorrent.exe
run-nordtorrent.cmd      launcher: data/ and downloads/ next to the exe
README.txt               Windows quick start, firewall, HTTPS, ffmpeg
README.md, README.da.md, LICENSE
```

## Build the source zip locally

The simplest way to get a source archive is GitHub itself: every release has **Source code (zip)**. For a local archive:

```powershell
git archive --format=zip --prefix="nordtorrent-0.1.0/" -o nordtorrent-0.1.0-source.zip HEAD
```

The maintainer uses `scripts/release_to_github.ps1 -Zip` for this. It assembles the publishable tree and refuses to finish if `scripts/`, `data/`, `downloads/`, `.env`, `dist/` or any server-specific string leaks into the copy. That script is local-only as well.

## Manual upload

If Actions cannot build (for example a Windows toolchain problem), create the release by hand:

1. Push the tag as above; the source archives are generated by GitHub.
2. Run the packaging steps above and upload `dist/nordtorrent-<version>-windows-x64.zip`.
3. Upload the `nordtorrent-<version>-source.zip` you created with `git archive` if you want a source archive with the same folder layout as the Windows zip.

## Versioning

`server/Cargo.toml` is the single source of truth: both workflows read the version from it, so asset names, tag and binary version stay in sync.
